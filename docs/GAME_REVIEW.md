# ゲームレビュー — Dice Board Rogue

対象: `claude/game-review-y2hu81` (`7a8ee47` 時点) / 実測日 2026-08-26

検証方法: Godot 4.4.1 headless で `tests/` 全7本を実行（**全て 0 failure**）したうえ、
再現用の使い捨てスクリプトを書いて各項目を実際に走らせている。
「実測」と書いてある項目は推測ではなく実行結果。

---

## 総評

芯は良い。効果システムを `{on, op, amount, scale, cond}` のデータに落として
「マス48種・ダイス27種を1行追加で足せる」形にしてあるのは、この規模の
個人プロジェクトとしてかなり強い設計で、`_route_for_roll` をプレビューと
実移動の両方で共有しているおかげで「表示と挙動が食い違う」という
すごろく系で最も多い事故が構造的に起きないようになっている。
2タップ確定（1回目=情報、2回目=実行）もタッチ前提として正しい判断。

問題は**システムではなく、その上に乗っている運用**の側に集中している。
特に重いのが次の3点で、いずれも「今遊ぶと壊れる」レベル:

1. ボス敗北でマップが完全に詰む（進行不能）
2. 2階・3階の敵が1種類しか出ない（ゲームの2/3が同じ戦闘）
3. 敵ターンが二重に走る入力窓がある

以下、実測で確認できた順に。

---

## A. 進行不能・データ破壊クラス

### A-1. ボスに敗北すると探索マップが完全に詰む 🔴

`_enter_map_node` はボスノードだけ `cleared` にしない（Main.gd:5004-5005）。
これは「ボスは再挑戦できる」という意図のコメント通りなのだが、
`MAP_LAYOUT` のボスノードは `links: []`（Main.gd:5960）で、
`_is_map_reachable` は**現在地からのリンク先**しか返さない。
`_style_map_node` は `button.disabled = not reachable`（Main.gd:4978）。

つまりボス敗北 → `_resolve_fall` → 「探索へ戻る」→ ボスマスに立ったまま、
**盤上の全ボタンが disabled**。再挑戦どころか1マスも動けない。

実測:
```
[boss node cleared flag] false
[boss node links] []
[reachable nodes while standing on boss] []
```

修正案: `_is_map_reachable` に「未クリアの現在地自身」を含める
（1行で済み、再挑戦したいという元の意図とも一致する）。
探索移動の疲労は `_on_map_node_pressed` で加算されるので、
再挑戦にコストが乗るのも自然。

### A-2. 戦闘中にセーブされた状態から再開すると、戦闘が丸ごとスキップされる 🔴

`_enter_map_node` は `node["cleared"] = true`（5005）を
**`_save_run(true)`（5008）より前に**実行している。
そのため保存データは `in_node: true` かつ `cleared: true` になり、
`_load_run` → `_enter_map_node` → 冒頭の `if cleared: _show_map(); return` に落ちる。

コメントは「中断したノードに再入場する」と書いてあるが、実際は逆で、
**戦闘（強敵含む）を無傷でスキップして報酬だけ失う**。
負けそうな戦闘でアプリを閉じれば任意にスキップできるセーブスカムでもある。

実測（新規インスタンスに同じセーブを読ませた結果）:
```
[save in_node] true
[save node[1][2].cleared] true
[load_run succeeded] true
[state after resuming a save taken mid-fight] map   ← 戦闘に入らない
[enemies present after resume] 0
```

修正案: `_save_run(true)` を `cleared` 代入より前に出すか、
再入場判定を `in_node` 優先にする。

### A-3. 敵ターンが二重に走る入力窓（約0.6秒） 🔴

`_resolve_landing` は最後の行動を消費したあと、
`state = "player"` に戻して `_refresh_all()`（＝終了ボタンを再有効化）してから
`BEAT_PHASE` 0.6秒待ち、その後 `_enemy_turn()` を呼ぶ（Main.gd:6615-6619）。
`_on_end_turn_pressed` のガードは `state != "player"` だけなので、
この0.6秒の間にタップすると `_enemy_turn()` が**2本並走**する。

実測（3ダメージの確定攻撃敵に差し替えて計測）:
```
[window found: state/actions/end-turn-enabled] player / 0 / true
[player HP after the tap (start 20)] 15    ← 3ダメージの敵に2回殴られている
[run_turns (1 player turn played)] 3       ← _start_player_turn が2回走った
```

被弾・毒処理・再生・マス汚染・盾リセットが全部2回走る。
確定攻撃持ち（灼眼・深淵の主）相手だと事故死に直結する。

修正案: 待機中は `state` を `"resolving"` などに逃がすか、
`_enemy_turn` の先頭に再入防止フラグを置く。

## B. 死にコンテンツ・仕様と挙動の不一致

### B-4. 2階・3階に敵が1種類しか出ない 🔴（体験への影響が最大）

`_pick_enemy_for(row + (floor_index - 1) * MAP_ROWS, kind)`（Main.gd:5979）に対し、
中身は `span = row / (MAP_ROWS - 2)` = `row / 10`。
2階は row が 12〜23 になるので `span > 1` で必ず飽和し、
`clampi(base, 0, last - 1)` で全ノードが index 5（贄喰い）に固定される。

実測:
```
[floor 1 enemy indices] [1, 2, 3, 4, 5, 6]
[floor 2 enemy indices] [5, 6]
[floor 3 enemy indices] [5, 6]
```

しかも `_setup_encounter` に階層によるHP・攻撃力の補正が一切ないため、
**2階と3階は「1階の終盤の敵と同じステータスの贄喰い」を延々と繰り返すだけ**になる。
強敵ノードも同じ index 5 の1.5倍でしかない。

全3層のうち2層が同じ戦闘なので、これがゲームとして一番効いている欠陥。
`span` を `floor_index` 込みで正規化するか、階層ごとにHP/damage 係数を掛けるかの
どちらかは必須。

### B-5. 粘体（`enemy_defs[0]`）は一度も出現しない 🟠

`_pick_enemy_for` は `round(span * 5)`。敵が置かれる最小の row は 1 で
`round(0.1 * 5)` = `round(0.5)` = 1。つまり index 0 に到達する経路が存在しない。
上の実測で floor 1 が `[1, ...]` から始まっていることがそのまま証拠。

HP20/ダメージ5/デバフ無しという、明らかにチュートリアル用に作られた敵が
未使用のまま眠っていて、初戦がいきなり茨を撒く絡み蔦になっている。

### B-6. 跳躍（`vault`）ダイスの「+2歩」が完全に無効 🟠

`_on_die_pressed` は spend 効果を 6424 行で実行し（ここで `steps_left += 2`）、
そのあと 6438 行で `steps_left = absi(final_roll)` と**上書き**している。

実測: 出目2の跳躍ダイスで進んだ距離は **2マス**（説明文の「実質4から6の移動」なら4）。

このダイスは報酬プールにも店（25G）にも並ぶので、
プレイヤーは「何も起きないダイス」を報酬として選ばされる。
`_route_for_roll` 側も spend の `step` を見ていないので、プレビューも同じく2マスで、
表示と挙動が一致してしまっている分だけ気づきにくい。

なお通過型マスの `跳躍路` は `_route_for_roll` 内で処理されており、そちらは正常。

### B-7. 擬態箱の予告マスが1つ無駄になっている 🟡

`"cells": [2, 6, 10, 14]`（Main.gd:4721、mode `fixed`）だが、リングは12マスなので
14 は 2 に正規化される。

実測: `[(2,0), (3,3), (0,2), (2,0)]` → 実質3マスしか予告していない。
4マス予告のつもりの敵が、他の敵より弱くなっている。

16マスリング時代の名残で、同じ名残が `MAX_DEBUFFS` のコメント
（"five of sixteen" と書いてあるが値は 4、リングは 12）にも残っている。

### B-8. 店の品揃えを無料で引き直せる 🟡

`_resolve_shop_node` は毎回 `die_reward_pool` を `shuffle()` し直す。
「ダイスを1つ処分」→「やめる」は `_resolve_shop_node()` に戻る（Main.gd:5115）ので、
**出入りするだけで在庫2枠を好きなだけリロールできる**。
`_buy_die` 後の再表示（5100）も同様。

在庫は店ノードに入った時点で固定して `node` に持たせるのが素直。

## C. Web配信まわり

### C-9. `sw.js` は一度も登録されていない 🟠

`GODOT_CONFIG` に `serviceWorker` キーが無い（index.html:113）。
`Engine.installServiceWorker` は `this.config.serviceWorker` が無ければ即 return し
（index.js:866）、index.html 側のもう一方の呼び出しも
`GODOT_CONFIG['serviceWorker'] && ...` で門前払いされる（index.html:170）。

結果、**39MB の `index.wasm` を毎回フルダウンロード**している。
スマホブラウザを主対象に据えたゲームで、これは一番効くコストのはず。
`sw.js` 自体は `.pck` を `no-store` にしてキャッシュ汚染を避ける作りまで
できているので、`"serviceWorker": "sw.js"` を1行足すだけで意図通りに動く。

### C-10. 使われていない `.pck` が3本・27MB 🟡

`mainPack` は `index.stepmap.pck`。残りは:

| ファイル | 状態 |
|---|---|
| `index.pck` | `index.stepmap.pck` と**md5完全一致**（`6495e0fa…`）。純粋な重複 |
| `index.map12.pck` | 旧ビルド。参照なし |
| `index.616285f.pck` | 旧ビルド。参照なし |

`git count-objects` で pack 67.87 MiB。クローンのたびに死んだビルドを運んでいる。
`sw.js` の冒頭コメントも「index.pck がゲーム本体」と書いたままで、現状と食い違う。

### D-12. 英語ロケールが実質未実装 🟡

`i18n/strings.csv` は395行あるが、`en` 列は**全行空**。
Godot は空訳をソース文字列にフォールバックするのでクラッシュはしないが、
設定画面の「English」ボタンは押しても何も変わらない。

英語ボタンを**外す**のが誠実で、コストも一番低い。

## E. ゲームデザインとしての所見（バグではない）

### E-13. 盤の枠が11マスしかないのに報酬が多すぎる

配置可能なのはリング12マス − スタート1 = **11マス**。
一方で1階につき訪れるノードは11個で、その多く（battle / elite / chest / trap）が
マス報酬を出す。3層通すと報酬機会は20回を優に超える。

つまり2階の途中で盤は埋まり切り、以降のマス報酬は**すべて上書き**になる。
「盤を育てる」という一番おいしい部分が前半で終わってしまう。

- 案A: 後半の報酬を「既存マスの強化」に変える
- 案B: 2階以降でリングを拡張する（4x4 → 5x5 で16マス）
- 案C: 後半の報酬をダイス寄りに傾ける

### E-14. ダイス袋の希釈

`dice_bag` は報酬・店・イベントで増える一方で、除去は店の20Gのみ。
手札は3枚固定なので、袋が15枚になると盤面を組み立てた前提のダイスが
ほとんど回ってこない。デッキビルダーとしては普通の問題だが、
**除去手段が「たまたま店ノードを通れたら」しかない**のが薄い。
店ノードは各階に2つあるが、経路上で通れるのは多くて1つ。

### E-15. 現状、実質的に負けが存在しない

総陥落の条件は「疲労MAX(100) かつ ボスに敗北」。
探索での疲労は 1階あたり約11移動 × 2 = 22、3階で約66。
休憩は1回18回復。つまり**戦闘敗北を3回以上重ねないと100に届かない**。
そして A-1 の通り、ボス敗北はそもそも判定に到達する前にマップを詰ませる。

`docs/DESIGN_DIRECTION.md` §2 では敗北条件を
「昂りMAX時に敵の直接攻撃を受けたら敗北」に置き換えると**確定**扱いにしてあるので、
ここは方針側で解決される想定だと思う。ただし §2 の昂りゲージは
まだコードに入っていない（`Main.gd` に「昂り」の実装は無く、
文字列だけが `strings.csv:335` に存在する）。
方針文書の優先順位でも2番目に置かれている項目。

### E-16. 細かい所

- ヒーローは `knight`（シズク）1体のみ。mage / rogue はコメントアウトで保持。
  `hand_limit` や `actions_per_turn` をヒーロー属性にしてある設計は活きているので、
  復帰コストは低い状態を保てている。
- `hero_defs` のコメントに「three evenly spaced anchors」とあるが、
  配置は step 2 / 5 / 8（間隔 3・3・6）で等間隔ではない。
  12マスなら 0 / 4 / 8 が等間隔だが、スタート(0)には置けないので
  2 / 6 / 10 あたりが意図に近いはず。
- `大車輪`（7〜9歩）は12マスリングの3/4周にあたる。説明の「盤の半分以上」は正しい。
- `_damage_enemy` の装甲下限1、`_take_damage` の部位倍率が盾通過分にのみ乗る扱いは、
  どちらもコメント通りに実装されていて破綻していない。
